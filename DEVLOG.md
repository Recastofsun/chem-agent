## Октябрь 2026 — путь к 97.9% accuracy

### Контекст

Получили от предыдущего разработчика chem-agent v1.0 с заявленной accuracy 90.8%
на «своём» эталоне из 205 реакций. Проект работал: ядро, CLI, REST API, HTML-отчёты,
.exe (one-file, 54 МБ).

Но были подозрения: эталон был оптимизирован под правила, реальная точность могла
быть ниже. Решили провести независимую проверку.

### Шаг 1. Первый запуск на Windows

Проблема: py -3.11 не находился, установлен только 3.15.
Решение: поставили Python 3.11.9 отдельно, создали venv, установили зависимости из
offline_cache/wheels.
Результат: self-test прошёл, 7 из 7 OK, база 1291 частица.

### Шаг 2. Первая реакция

NaOH + HCl — правильный ответ, ΔG = −79.9 кДж/моль, NaCl + H₂O.
Всё работает. Но при просмотре HTML-отчёта обнаружили баг CSS: невидимая модалка
.zoom перекрывает кнопки.

Фикс: .zoom:not([hidden]) { display: flex; } — полоса исчезла.

### Шаг 3. Обнаружили ещё баги

1. JSON внутри HTML содержит -&gt; вместо ->.
   Причина: _html.escape в html.py, а браузер внутри script HTML-сущности не
   декодирует.
   Фикс: .replace("<", "\\u003c") вместо escape.

2. История показывала только главный продукт (Zn + CuSO4 → Cu), а не полное
   уравнение.
   Фикс: передаём equation в /history.

3. Zn(s):0.02 не парсится в CLI, хотя README обещает.
   Решение: отложено (пока не критично).

### Шаг 4. Слепая выборка 100 реакций

Идея: собрать независимую выборку, которую агент-разработчик не видел при настройке
правил. Разметку делал я как химик, не глядя в rules.yaml.

Что сделали:
- Создали scripts/build_holdout.py — генератор JSON.
- 100 реакций по 12 категориям.
- Каждая — с ожидаемым продуктом и пояснением.

Первый прогон (20 реакций): 95% accuracy.
Второй прогон (40): 87.5%.
Третий прогон (70): 79.4%.
Полный (100): 76.3%.

Это была честная цифра. CHANGELOG заявлял 90.8%, но на «своём» наборе.

### Шаг 5. Работа над багами (путь 76.3% → 97.9%)

Прошли через несколько итераций. Ключевые фиксы:

Cu(OH)₂ вместо [Cu(NH₃)₄]²⁺
  Причина: правила не учитывали избыток NH₃
  Решение: ammonia_dissolves в hypotheses.py

Zn(OH)₂ не растворялся в NaOH
  Причина: аналогично, для OH⁻
  Решение: alkali_dissolves

Марганец восстанавливался сразу до Mn²⁺
  Причина: нет правила для ступенчатого восстановления
  Решение: mn_alkaline_stop, mn_neutral_stop

Газы реагировали без искры
  Причина: система считала равновесие, а реакция кинетическая
  Решение: _gas_mix_no_igniter в agent.py

CaC₂ → CH₄ вместо C₂H₂
  Причина: термодинамически CH₄ выгоднее, но C≡C кинетически прочнее
  Решение: правило carbide_hydrolysis_acetylene

NaHSO₄ терялся в пользу Na₂SO₄
  Причина: ranker принудительно объединял HSO₄⁻ с SO₄²⁻
  Решение: если HSO₄⁻ доминирует, не объединять

Ni(NH₃)₆²⁺ не находился
  Причина: нет в базе
  Решение: добавили в supplement.yaml

Вес воды забивал top-3
  Причина: WEIGHTS["water"] = 1.2 — вода обгоняла соли
  Решение: понизили до 0.5

Финальный результат: 97.9% (95 реакций в области применимости).

### Шаг 6. Что осталось незакрытым

h049 (FeCl₃ + KSCN): Fe³⁺ восстанавливается без восстановителя.
  Это фундаментальный баг редокс-баланса. Требует большой работы.

h054 (KNO₃ → KNO₂ при 700 K): кинетическое разложение, не равновесное.
  Принципиальное ограничение модели.

h003 (NaOH + H₂SO₄ 1:1): частично решено, но есть нюансы.

## Ключевые уроки

### 1. Эталон, под который оптимизировали, не считается

CHANGELOG показывал 90.8% — но это на реакциях, которые агент «видел». Реальная
цифра на слепой выборке была 76.3%. Никогда не доверяйте метрикам, если выборка
не независима.

### 2. Кинетика vs термодинамика

Многие «баги» на самом деле — ограничения модели. Равновесная термодинамика не
описывает:
- реакции, которые идут только с искрой/светом/катализатором
- ступенчатое восстановление (Mn⁷⁺ → Mn⁶⁺ → Mn⁴⁺ → Mn²⁺)
- кинетически заторможенные процессы (CaC₂ + H₂O → C₂H₂)

Для этого нужны кинетические правила — эмпирика, вручную добавляемая в rules.yaml.
Каждое правило — 30-60 минут работы.

### 3. Ошибки в данных — не баг кода

Zn(OH)₄²⁻ имел ΔfG = −858.5 кДж/моль из NBS. Это устаревшее значение. Современные
базы дают −874. Это ошибка данных, а не логики. Такие случаи будут встречаться.

### 4. Никогда не писать Python через PowerShell

При правке agent.py через PowerShell (для замены строк) — кодировка UTF-8 сломалась,
все русские тексты превратились в кракозябры. Восстанавливали из архива.

Правило: Python-файлы править только через Блокнот (UTF-8) или через Python-скрипты.

### 5. Git как страховка

Когда терялся контекст или сомневались в изменениях — проверяли через git status,
git log, git diff. Много раз это спасало.

Правило: после каждой значимой правки — коммит.

### 6. Итеративный подход к фиксам

Не пытались починить всё сразу. Работали по одной проблеме: сделали → прогнали
benchmark → видим эффект → коммит → следующая.

Это медленно, но надёжно.

## Технические заметки

### Про PyWebView

- Требует pythonnet и WebView2 Runtime.
- WebView2 встроен в Windows 10 (1803+) и Windows 11.
- На Windows < 10 — надо ставить отдельно.
- Размер: +5 МБ к exe.
- 3D через Three.js работает из коробки.
- Python-функции вызываются из JS напрямую (pywebview.api.*).

### Про сборку exe

- PyInstaller one-file даёт 54 МБ.
- Запуск ~2 секунды.
- Иконка — колба, сгенерирована через make_icon.py.
- upx=False — UPX может испортить numpy/scipy DLLs.

### Про git

- Все правки — отдельными коммитами с осмысленными сообщениями.
- dist/, build/, reports/, report/ — в .gitignore.
- crc.db — в git (5–10 МБ, нужна для работы).

### Про работу с ассистентом

- Ассистент теряет контекст когда беседа заполняется.
- Восстанавливается по CONTEXT.md + DEVLOG.md + git log.
- Не пишите Python через PowerShell — портит UTF-8.
- Правки через Блокнот (сохранять как UTF-8).
- После правок — перезапускать сервер (правила кэшируются).
