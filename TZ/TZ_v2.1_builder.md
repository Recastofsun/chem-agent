# ТЗ: Chem-Agent v2.1 (Molecule Builder & Rule Audit)

## 1. Цель проекта
Добавить интерактивный инструмент («Визуальный конструктор») для 2D/3D-сборки молекул, а также провести **системный аудит кинетических правил (`rules.yaml`)** для устранения точечных «заплаток» и улучшения предсказуемости ядра.

## 2. Архитектура и Ядро (Backend)
Модуль: `chem_agent/parser/builder.py`

### 2.1. Графовая структура (прицел на органику)
Молекула представляется как математический граф:
*   **Узлы (Nodes):** Атомы (элемент, заряд).
*   **Ребра (Edges):** Химические связи (индекс атома 1, индекс атома 2, тип связи: одинарная, двойная, тройная).
*   *Почему так:* Это универсальный формат (SMILES/Molfile), который в будущем позволит легко подключить библиотеку `RDKit` для органики без переписывания UI.

### 2.2. Движок валентностей (Valency Engine)
*   Таблица базовых валентностей (`H:1, O:2, N:3, C:4, Cl:1` и т.д.).
*   Валидация: если пользователь пытается создать связь, превышающую лимит (например, `H-H-H`), ядро возвращает ошибку.
*   Автодополнение: функция «Добавить водороды» (пользователь нарисовал `O`, нажимает кнопку, и ядро само дорисовывает `H2O`).

### 2.3. Генерация 3D-координат
*   Поскольку в базе `crc.db` нет 3D-структур для всех возможных комбинаций, ядро должно уметь генерировать простые координаты для 2D-графа (например, тетраэдр для `CH4`, плоскость для `H2O`).

## 3. Интерфейс (Frontend)
Новый экран: `#builder` (Визуальный конструктор).

*   **Рабочая область:** 2D-холст с зумом и панорамированием.
*   **Панель элементов:** Список доступных элементов.
*   **Режимы связей (настраивается в Настройках):** Клик-соединение или Drag-and-drop (протяжка).
*   **Переключатель 2D/3D:** Кнопка, которая перерисовывает текущий граф в 3D (Three.js).
*   **Интеграция:** Кнопка «Отправить в Конструктор реакций» (передает формулу в `localStorage`).

## 4. Системный аудит `rules.yaml` и ядра
**Вместо точечных фиксов мы проводим рефакторинг логики правил.**

### 4.1. Обобщение правил (Классификация вместо перечисления)
*   **Проблема:** Сейчас правила часто ссылаются на конкретные вещества (например, `FeCl3 + KSCN`). Это не масштабируется.
*   **Решение:** Ввести классы/теги для веществ в базе (например, `strong_oxidizer`, `transition_metal`, `amphoteric_hydroxide`). Правила должны описывать взаимодействие *классов*, а не отдельных молекул. (Например: «Если есть `strong_oxidizer` и `halide`, реакция идет, если нет `reducer`»).

### 4.2. Разрешение конфликтов правил (Приоритеты)
*   **Проблема:** Если одно правило разрешает реакцию (термодинамика), а другое запрещает (кинетика), кто победит?
*   **Решение:** Ввести строгую иерархию (Hard Blockers > Soft Blockers > Thermodynamic Propensity > Proceed). Задокументировать, как `rules.py` выбирает победителя.

### 4.3. Аудит и удаление «мертвых» правил
*   Проверить `rules.yaml` на предмет дубликатов или правил, которые никогда не срабатывают из-за более сильных ограничений. Создать скрипт `scripts/audit_rules.py` для вывода статистики по срабатываниям.

### 4.4. Решение накопленных багов через новую логику
*   **h049 (Fe3+ + SCN-):** Вместо хардкода проверяем наличие в системе явного восстановителя (через классы веществ), иначе `redox` переводится в состояние `blocked`.
*   **h054 (KNO3 -> KNO2):** Добавить в ядро и UI флаг `open_system` (открытая система), который обнуляет парциальное давление газов-продуктов, позволяя энтропийному фактору вытянуть реакцию разложения.
